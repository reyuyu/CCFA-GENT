# 九、Introduction 检查 Skill 的设计

## 1. 设计目标

`checking-introduction-skill` 是 `PaperCheckAgent` 中专门负责检查 Introduction 的 skill。

它的目标不是直接改写 Introduction，而是模拟一个第一次阅读该部分的学术读者，判断用户指定的段落、句子或单词是否：

- 能被读懂。
- 有足够参考支撑。
- 与上下文逻辑连贯。
- 与科学问题、创新点和 Introduction 大纲对齐。
- 概念和术语前后一致。
- 语气和程度表达合适。
- 值得保留、需要局部修改，还是需要补充材料后再改。

这个 skill 的默认输出是检查意见、依据和建议。只有用户明确确认需要修改时，才允许进入 patch 生成流程。

## 2. Skill 基本信息

建议注册信息如下：

```text
Skill ID: checking-introduction-skill
Skill Name: IntroductionCheckSkill
Targets: introduction, motivation, research gap, contribution, related work framing, problem formulation
Description: Check Introduction paragraphs, sentences, and terms through reference grounding, logic, concept consistency, information alignment, tone, length, and first-reader readability.
```

建议目录结构如下：

```text
app/skills/checking-introduction-skill/
  SKILL.md
  checklists/
    sentence-level-checklist.md
    word-level-checklist.md
    evidence-checklist.md
  rubrics/
    introduction-quality-rubric.md
  examples/
    README.md
```

## 3. 检查原则

### 3.1 段落状态先验原则

检查前必须先读取目标段落的写作状态。

如果目标段落已经是 finalized、final 或 locked 状态，该段落应更多作为已经定稿的先验上下文，而不是严格审查对象。

对定稿段落的处理原则是：

1. 不做过度挑错。
2. 不主动建议大改。
3. 不在没有用户明确要求时提出重写建议。
4. 主要检查它与用户当前关注内容之间的上下文关系。
5. 如果定稿段落存在会影响后续理解的明显问题，只能温和指出为“上下文风险”。

例如：

```text
这部分如果已经定稿，我不会建议直接重写；但从后文衔接角度看，它对 X 概念的铺垫略弱，因此后续段落第一次提到 X 时需要补一个轻量解释。
```

这个原则的目的，是避免 Agent 对用户已经确认过的论文部分反复推翻，保护论文工程的稳定性。

### 3.2 逐句检查原则

如果用户检查的是段落、句子组或整个 Introduction，必须逐句检查。

每一句至少从以下维度判断：

1. 参考维度。
2. 逻辑维度。
3. 概念维度。
4. 信息对齐维度。
5. 语气维度。
6. 其他维度。

逐句检查不是简单给每句话打分，而是要判断这句话在 Introduction 中是否承担了合理功能，以及是否与前后句形成可读的学术推进。

### 3.3 输出依据原则

检查后必须向用户给出详细检查结果、依据和建议。

依据可以来自：

1. 当前目标文本。
2. 目标句子的上一句和下一句。
3. 前后段落。
4. Introduction 大纲。
5. 科学问题记忆、创新点、关键技术记忆。
6. 核心参考论文和普通参考论文。
7. 用户明确提供的写作目标。

如果缺少依据，必须明确说“当前材料不足以判断”或“当前材料不足以支撑该句 claim”。

不能把没有读到的参考论文内容当作依据。

### 3.4 成本原则

检查报告最后必须给出总体检查结论和总体感觉。

这里的“成本”主要指用户继续修改这段内容的成本：

- 是否只是低成本局部调整。
- 是否需要中等成本重排句子逻辑。
- 是否需要高成本补充参考材料或重构段落。
- 是否暂时不值得改，因为该段已经定稿或当前问题很轻。

总体结论要帮助用户做决策，而不只是堆问题。

推荐结论类型：

```text
总体感觉：基本能读懂，但 gap 的证据支撑不够，建议补参考后再修改。
修改成本：中等。主要需要补强 S3-S4 的参考依据和逻辑过渡，不需要推翻整段。
建议动作：先补充一篇 concept grounding 相关参考，再局部改写后半段。
```

### 3.5 第一印象开头原则

回答的开头必须是第一印象。

开头固定模拟第一次阅读者的感受，格式建议为：

```text
假如我第一次阅读到这里，我的感觉是：……
```

这个第一印象必须回答一个核心问题：

```text
第一次读者能不能读懂？
```

第一印象可以包含：

- 是否能顺着读下去。
- 是否知道这一段想说明什么。
- 是否知道这句话为什么出现在这里。
- 是否觉得某个概念突然出现。
- 是否感到证据不足或语气过强。

示例：

```text
假如我第一次阅读到这里，我的感觉是：这段大体能读懂，也能看出作者想从 X 推到 Y；但读到第三句时，我会停一下，因为这里突然把 limitation 提升成 research gap，却还没有看到足够参考或上下文证据。
```

### 3.6 参考相似度与引用状态区分原则

检查 Introduction 时，不能把“论文句子和参考论文句子相似度高”本身当成问题。

如果某句话是在使用参考论文作为 source-grounded writing material，或者是在 imitation 高质量论文的学术表达、段落推进方式、概念表述方式，那么它和参考论文中的句子相似度较高是允许的。检查重点不是“像不像”，而是：

1. 是否符合当前论文的科学问题、术语和上下文。
2. 是否改变了参考论文原意。
3. 是否把参考论文中的概念错误迁移到当前论文。
4. 是否存在过长照搬导致的版权或学术不规范风险。

同时，要区分“参考支撑”和“正式引用状态”。

参考论文不一定必须已经是 manuscript 中的正式参考文献。它可以先作为本地语料、写作来源、概念来源或判断依据使用。除非用户明确要求检查 citation 或引用格式，否则不需要逐句检查每句话是否有显式引用，也不需要要求 Introduction 每一句都带 citation。

参考维度的重点应放在关键 claim、背景事实、gap 句、概念定义、强语气表达是否有材料支撑。普通过渡句、作者自己的 contribution framing、已经由上下文承接的信息组织句，通常不需要做逐句引用状态检查。

## 4. 工作流程

### 4.1 锁定检查对象

第一步必须定位用户需要检查的对象。

检查对象可能是：

1. 整个 Introduction。
2. Introduction 的某个段落。
3. 某个段落中的一句话。
4. 某个句子中的一个单词或短语。
5. 某个逻辑单元，如 motivation、gap、contribution。

需要调用工具读取：

```text
list_draft_sections
list_draft_paragraphs
get_draft_paragraph_content
get_draft_paragraph_status
get_introduction_outline
get_scientific_problem_memory
```

如果用户只给出一句话或一个单词，Agent 应在 Introduction 中定位它属于哪个段落，以及该段是否定稿。

如果无法定位，应先说明无法确定上下文，并请求用户指定段落或提供前后文。

### 4.2 判断段落状态

定位目标后，必须检查段落状态：

```text
todo / draft / final / finalized / locked
```

如果是 finalized、final 或 locked：

```text
将它作为先验上下文，除非用户明确要求，否则不做严格逐句批判和修改建议。
```

如果是 draft 或 todo：

```text
正常进入逐句多维度检查。
```

### 4.3 段落或句子检查

如果用户检查的是段落或句子，必须逐句分析。

每一句都应形成一个检查单元：

```text
S1: 原句或句子摘要
  参考维度：
  逻辑维度：
  概念维度：
  信息对齐维度：
  语气维度：
  其他维度：
  结论：
  建议：
```

如果某一句没有问题，不需要硬挑问题，但仍要说明它为什么可以保留。

例如：

```text
S1 可以保留。它承担背景引入功能，和段落任务一致；但如果后文要把 X 作为核心 gap，最好在 S1 或 S2 中提前铺垫 X 的定义。
```

### 4.4 单词或短语检查

如果用户检查的是单词或短语，也必须进行多维度分析。

重点检查：

1. 这个词是否符合当前句子的语义。
2. 是否与上下文术语一致。
3. 是否与参考论文常见表达一致。
4. 语气强度是否合适。
5. 是否可能造成概念混淆。
6. 是否有更合适的替代表达。

输出格式建议：

```text
目标词：robust
所在句子：...
第一印象：这个词能读懂，但语气偏强。
参考维度：本地参考中如果没有明确 robustness 实验证据，不建议使用。
概念维度：如果全文主要讨论 generalization，不应在这里突然换成 robustness。
语气维度：robust 暗示强可靠性，证据不足时可换成 more reliable / less sensitive / improved。
建议：除非结果部分有 robustness analysis，否则建议改为 ...
```

### 4.5 语料不足时的学术调研

如果本地参考论文和项目材料不足以判断或支撑某个 claim，可以考虑帮作者做一次学术调研。

这里的调研不是自动改稿，而是寻找可能补充证据的论文。

流程：

```text
发现材料不足
  -> 明确说明缺少哪类证据
  -> 询问或建议调用 retrieve_academic_papers
  -> 如果用户已授权检索，调用 retrieve_academic_papers
  -> 返回候选论文和它们可能支撑的检查点
  -> 用户确认后，才能把这些论文当作后续写作依据
```

材料不足的常见类型：

- 缺少背景事实证据。
- 缺少 gap 是否真实存在的证据。
- 缺少方法类别或概念定义来源。
- 缺少与创新点对应的对比论文。
- 缺少实验结果支撑。
- 缺少术语使用依据。

### 4.6 整理证据并组织回答

最终回答必须包含三层：

1. 模拟第一次阅读者的第一印象。
2. 具体分析、建议和依据。
3. 总体结论和修改成本判断。

不允许只输出一句“整体不错，但建议加强逻辑”。

## 5. 多维度分析规则

### 5.1 参考维度

逐句检查时，需要先调用工具查看核心参考论文和参考论文元信息，但这个检查不是逐句 citation audit。

推荐工具：

```text
list_reference_papers
list_reference_sections
get_reference_section_content
```

检查目标：

1. 用户是否明确提供了相关本地参考论文。
2. 核心参考论文中是否有对应背景、概念、gap、方法或 claim。
3. 当前关键句子是否有参考证据或项目事实支撑。
4. 是否存在没有来源的强主张。
5. 是否把参考论文没有说的内容写成了事实。
6. 如果句子与参考论文相似度较高，判断它是否仍然符合当前论文语义、上下文和学术规范，而不是直接判为问题。

原则：

```text
如果用户明确有相关本地参考信息，必须严格检查句子与参考之间是否对应。
一般情况下，Introduction 中的关键 claim 需要相关参考证据或项目事实支撑。
非必要时，不检查每一句的正式引用状态。
```

不同句子的参考要求不同：

- 背景事实句：通常需要来源支撑，但不一定逐句检查 citation。
- 领域现状句：需要来源支撑。
- gap 句：强烈需要参考或多篇论文对比。
- contribution 句：需要与当前论文实际方法和创新点对齐，不一定需要外部参考，但需要项目事实支撑。
- 过渡句：可以不直接引用参考，但不能引入无依据事实。

输出时要区分：

```text
有明确参考支撑
有本地参考语料支撑，但尚未确认是否进入正式参考文献
有弱相关参考，但还不够严格
本地参考不足，建议补充
当前句子是作者自己的 contribution framing，不需要外部参考，但需要与项目事实一致
句子与参考论文相似度较高，但语义迁移合理，可以接受
```

### 5.2 逻辑维度

逐句检查时，要仔细检查当前句与上一句是否有明确逻辑对应。

重点判断：

1. 当前句是否承接上一句。
2. 当前句是否提前引入了下一步论证所需的信息。
3. 是否缺少 therefore、however、despite、nevertheless、in contrast、in particular 等逻辑关系提示。
4. 是否存在跳跃：从背景突然跳到 gap，从 gap 突然跳到方法，从问题突然跳到贡献。
5. 是否存在重复：两个句子表达同一层信息，没有推进。
6. 是否存在循环论证：用结论解释结论。

如果当前句是段首句，还要检查：

```text
它是否承接上一段结尾。
它是否清楚开启了本段任务。
```

如果当前句是段尾句，还要检查：

```text
它是否完成本段任务。
它是否为下一段留下合理入口。
它是否过早抛出后文才解释的概念。
```

### 5.3 概念维度

逐句检查时，如果句子中有具体概念词汇，必须检查它们是否与上下文对齐。

重点检查：

1. 同一语义是否在上下文中用了不同表达，导致读者混淆。
2. 一个术语是否第一次出现却没有解释。
3. 概念层级是否混乱，例如 task、problem、method、module、metric 混用。
4. 方法名、问题名、数据集名、疾病名、任务名是否前后一致。
5. 是否把参考论文中的概念迁移到当前论文时改变了含义。

示例：

```text
如果前文一直使用 concept-based explanation，后文突然写 semantic cue grounding，需要检查这两个词是不是同一概念。如果是同一概念，应统一；如果不是，应说明差异。
```

### 5.4 信息对齐维度

逐句检查时，一定要检查写作是否切题，是否与创新点和科学问题对齐。

需要读取：

```text
get_introduction_outline
get_scientific_problem_memory
```

重点检查：

1. 当前句是否服务于 Introduction 大纲中的本段任务。
2. 当前句是否与论文科学问题一致。
3. 当前句是否为创新点铺垫，而不是偏向无关背景。
4. 当前句是否引入了论文不打算解决的问题。
5. 当前句是否承诺了 Method 或 Result 中没有兑现的内容。
6. 当前句是否与用户当前检查目标一致。

典型问题：

```text
这句话本身是对的，但它偏向 general medical AI，而当前论文的科学问题是 concept grounding，因此会稀释 Introduction 主线。
```

### 5.5 语气维度

逐句检查时，要检查程度用词是否过度或过轻。

重点检查：

1. 是否使用过强表达：significantly、substantially、robustly、comprehensively、fully、guarantee、solve。
2. 是否使用过弱表达：may、might、somewhat、a little，如果该句本应明确指出问题。
3. 是否把局部现象写成普遍事实。
4. 是否把可能性写成确定性。
5. 是否用营销化表达替代学术表达。

语气判断必须和证据绑定：

```text
如果有实验和参考支撑，可以使用更强表达。
如果没有支撑，应降级为更克制的 academic wording。
```

示例：

```text
原词 significantly improves 如果没有结果支撑，应改为 aims to improve、is designed to improve，或删除 significantly。
```

### 5.6 其他维度

其他维度用于补充上述维度没有覆盖的问题。

包括：

- 篇幅是否合适。
- 句子是否过长。
- 信息密度是否失衡。
- 是否有语法问题。
- 是否有中式英文痕迹。
- 是否有重复表达。
- 是否与目标 venue 的 Introduction 风格不一致。
- 是否需要拆句、合句或调整段落位置。

## 6. 回答结构

`checking-introduction-skill` 的回答必须按以下结构组织。

### 6.1 第一印象

必须放在回答开头。

```text
假如我第一次阅读到这里，我的感觉是：……
```

这一段不应过长，但要直观说明：

- 能不能读懂。
- 哪里卡住。
- 第一遍读者会不会知道作者想表达什么。

### 6.2 检查范围和状态

说明检查对象和段落状态。

```text
检查对象：Introduction P2，S1-S4。
段落状态：draft，因此我会做严格逐句检查。
使用上下文：P1 结尾、P2 全段、Introduction 大纲、科学问题记忆、核心参考论文 A/B。
```

如果是 finalized：

```text
段落状态：finalized。我会把它主要作为定稿上下文，只指出会影响后文理解的风险，不建议直接大改。
```

### 6.3 逐句多维度检查

每句建议使用紧凑但完整的格式：

```text
S1: "..."

- 参考维度：...
- 逻辑维度：...
- 概念维度：...
- 信息对齐维度：...
- 语气维度：...
- 其他维度：...
- 建议：保留 / 局部修改 / 补参考后再改 / 建议删除或移位。
```

如果篇幅太长，可以对没有问题的维度合并：

```text
参考和逻辑维度都基本成立；主要问题在概念维度。
```

但不能跳过关键句子的参考和逻辑判断。

### 6.4 证据整理

单独整理依据，避免用户看不出检查从哪里来。

```text
依据：
1. 草稿依据：S2 把 X 写成领域共识，但 P1 没有铺垫 X。
2. 大纲依据：P2 的任务是引出 concept grounding gap，而 S3 转向 general diagnosis robustness。
3. 参考依据：核心参考 A 支持 X 的背景，但没有支持 Y 的强结论。
4. 缺失依据：本地参考中暂未看到直接证明 Z 的材料。
```

### 6.5 修改建议

给出可操作建议，但不直接生成改稿，除非用户授权。

建议可以分为：

- 保留。
- 替换词。
- 补过渡。
- 补参考。
- 移到其他段落。
- 降低语气强度。
- 等用户补材料后再改。

### 6.6 总体结论和成本判断

最后必须给总体感觉和修改成本。

```text
总体结论：这段基本能读懂，但第三句的 gap claim 支撑不足，第四句与创新点对齐不够紧。
修改成本：中等。前两句可保留，后两句需要补参考和重排逻辑。
建议动作：先补充与 X limitation 直接相关的参考，再局部修改 S3-S4。
```

## 7. 编辑权限

`checking-introduction-skill` 默认只检查，不修改。

不允许修改的情况：

1. 用户只要求检查或评价。
2. 用户只要求建议。
3. 段落已经 finalized，用户没有明确授权。
4. 材料不足，修改会导致编造。

允许生成 patch 的情况：

1. 用户明确说“按检查意见修改”。
2. 用户明确要求“检查后生成修改 patch”。
3. 用户明确授权修改 finalized 段落。
4. 所需参考、上下文和项目信息足够支持修改。

生成 patch 时必须调用 edit tools：

```text
edit_draft_section
edit_draft_paragraph_content
edit_draft
```

最终写入仍由前端确认。

## 9. 当前设计的价值

`checking-introduction-skill` 让 Introduction 检查从“泛泛评价”变成可复核的逐句诊断。

它的价值在于：

1. 用段落状态保护已经定稿的内容。
2. 用第一印象模拟真实读者的阅读体验。
3. 用逐句多维度检查定位具体问题。
4. 用参考维度约束 Introduction 的证据基础。
5. 用逻辑、概念、信息对齐和语气维度保证论文主线稳定。
6. 用总体结论和修改成本帮助用户决定下一步是否改稿。

整体上，这个 skill 不只是检查英文是否通顺，而是检查 Introduction 是否像一段可靠的论文论证。
